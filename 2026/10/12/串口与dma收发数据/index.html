串口与dma收发数据

分析串口在开启dma时，如何进行数据的收发

环境

  • linux：5.10.227
  • 串口：pl011
  • dma：pl330

Linux 5.10 ARM PL011 串口 RX DMA 接收流程与硬件 FIFO 溢出问题 笔记

PL011 + PL330 / PL080，主线驱动 amba-pl011.c

结论速览

  1. PL011 的 RX DMA 是「单描述符、非 cyclic」：每次提交一个 scatterlist 条目，长度 PL011_DMA_BUFFER_SIZE = PAGE_SIZE（4K 页内核 = 4096 字节）。
  2. DMA 完成中断在「整页搬满」时才产生一次；不足一页不会有 DMA 中断。
  3. 不足一页的数据靠 PL011 自己的 RTI（接收超时中断）交付。
  4. 「FIFO 到了水位就搬、一次一个 burst」是硬件 + DMAC 行为，与 CPU 无关。
  5. PL011 + PL330 在 Linux 5.10 下属于「健康路径（状态 A）」：水位 16 > burst 8，DMA 不会把 FIFO 抽干，RTI 必定会触发。
  6. 针对硬件 FIFO 溢出（OE）：假设 DMA 正常运行，开 DMA 可以规避。原理：读走 FIFO 的动作从「CPU 在中断里响应」变成「硬件到水位自动搬走」。

2. 接收流程（DMA 模式）

2.1 启动

pl011_startup → pl011_dma_startup → pl011_dma_probe（申请 tx/rx 通道、slave_config）→ 置 DMAONERR → pl011_dma_rx_trigger_dma()：

pl011_enable_interrupts() 里 im = RTIM（DMA 在跑时不再补 RXIM），也就是 DMA 模式下只有超时中断和 modem 中断能打断 CPU。

2.2 硬件握手（无中断、无 CPU）

RX FIFO 超过水位 → PL011 断言突发请求 → DMAC 按 burst 搬运 → FIFO 降回水位下 → 请求撤销 → 再涨到水位再搬……直到整页（4096）搬满 → DMA 完成中断。

2.3 路径 A：整页搬满 → DMA 完成中断 → pl011_dma_rx_callback()

2.4 路径 B：不足一页 → RTI（接收超时中断）→ pl011_int → pl011_dma_rx_irq()

2.5 路径 C：接收错误（OE/BE/PE/FE）

因为 DMAONERR 已置位，硬件会自动停掉 RX DMA 请求，数据堆在 FIFO；驱动的错误中断位（OEIM/FEIM/…）并未使能，最终仍走 RTI 路径，由 pl011_dma_rx_chars() 里的：

清标志，然后重新 trigger DMA。

2.6 路径 D（可选）：poll 定时器

见第 6 节。

3. DMA 中断到底要多少数据才触发

  • 一次 DMA 完成中断 = 一个描述符搬完 = PL011_DMA_BUFFER_SIZE = PAGE_SIZE
    • 4K 页内核：4096 字节
    • 16K / 64K 页内核：16384 / 65536 字节
  • 每个 burst（8 字节）、每次水位跨越，都不产生中断。
  • 非 cyclic、只有一个 sg entry，所以没有半传输中断。
  • 不足一页的数据：不会产生 DMA 中断，只能靠 RTI 交付。

DMA 完成回调里的注释印证：

“This completion interrupt occurs typically when the RX buffer is totally stuffed but no timeout has yet occurred.”

4. RTI（接收超时中断）的触发条件

ARM 文档原文（Linux/QEMU/Xen 多方引用一致）：

“The receive timeout interrupt is asserted when the receive FIFO is not empty, and no more data is received over a 32-bit period. The receive timeout interrupt is cleared either when the FIFO becomes empty through reading all the data (or by reading the holding register), or when a 1 is written to the corresponding bit of the UARTICR register.”

拆解：

  1. IMSC.RTIM = 1（bit6）—— 软件使能；Linux 在 DMA 模式下始终保留
  2. RIS.RTIS = 1（bit6）—— 硬件条件：FIFO 非空 + 32 bit 时间无新数据
  3. LCR_H.FEN = 1 —— FIFO 模式（驱动 fifosize > 1 时必置）
  4. IRQ 线路通（合并 UARTINTR 或独立 UARTRTINTR）

时间与波特率相关，32 个 bit 时间 = 32 / baud：

  • 115200 → 约 278 µs
  • 9600 → 约 3.33 ms
  • 300 → 约 107 ms

要点：

  • 每收到一个新字符，32 bit 时间的计数器就重新开始（连续的流永不超时）。
  • 判据是「FIFO 非空」这个状态，与是否跨过 IFLS/RXIS 阈值无关。
  • FIFO 被读空 → 条件不成立，中断自动撤销；也可写 ICR.RTIC 清。
  • Linux 的 pl011_int() 特意不把 RTIS/RXIS 写进 ICR：

靠把 FIFO 读空自然撤销，避免误清丢事件。

  • ST 变体有可编程超时寄存器 ST_UART011_TIMEOUT（偏移 0x0C），主线驱动不用。

5. 关键判据：水位（IFLS）与 burst（maxburst）的大小关系

PL011 有四条 DMA 请求线（refman 原文）：

  • UARTRXDMASREQ：单字符请求：FIFO 含至少 1 个字符即断言
  • UARTRXDMABREQ：突发请求：FIFO 字符数超过 IFLS 编程的水位时断言
  • UARTRXDMACLR：由 DMAC 断言，清除接收请求；突发传输时在 burst 最后一个数据传输期间断言

所以「一次搬多少」= DMAC 配的 burst 长度，不是「FIFO 里有多少」。burst 是不可打断的传输组，做完才重新采样请求线。

配置 一次授权后 FIFO 留尾巴 RTI
水位 16 > burst 8（Linux 默认） 16 → 8，请求撤销 留 8~15 字节 必触发
水位 16 = burst 16 16 → 0 抽干 不触发
水位 4 < burst 8 4 → 0（整数倍搬空） 抽干 不触发

三种状态：

  • 状态 A（健康）：停手时 FIFO 非空 → RTI 必来 → 数据不丢不延迟。
  • 状态 B（延迟）：FIFO 被抽干但后续还有数据 → 下一批触发 RTI 或整页满才交付。
  • 状态 C（滞留）：FIFO 被抽干且对端不再发 → 数据卡在 DMA buffer，上层读不到。

历史佐证（2013 LKML「PL011 Rx DMA buffer polling」讨论）：

  • Chanho Min：4096 字节由 DMA 中断收到，但剩下 904 字节拿不到，除非再来 3192 字节。（状态 C）
  • Linus Walleij：理论上 16 个字符会被两个 burst 搬空、FIFO 为空、页未满，既无 TC 中断也无 RTI；但他在 U300/Ux500 上从未复现，怀疑 PL011 IP 在 burst 信号逻辑上做了处理。
  • Russell King：在 Versatile（PL080+PL011）上确实遇到，最后选择完全不开 RX DMA。

结论：PL011 水位 16 > burst 8，每次授权后 FIFO 从 ≥16 掉到 ≥8，请求撤销，停手时必留 8~15 字节 → RTI 必触发 → 状态 A（健康路径）。2013 年 Linus 担心的「整数倍突发被搬空」在这个组合下不会发生。

附带结论：

  • residue_granularity = DMA_RESIDUE_GRANULARITY_BURST，且 pl330_tx_status() 通过读 SA/DA 寄存器算出字节级 residue，满足 PL011 驱动的前置要求。
  • arm,pl330-periph-burst quirk 对 PL011 RX 无影响（burst_len 已是 8 > 1）；它只对 burst_len == 1（maxburst 配成 1）的场景有意义。
  • 唯一无法从代码确定的是 SoC 把 PL011 的哪根请求线接到 PL330：
    • 接 UARTRXDMABREQ（水位型）→ 与 BURST cond 匹配 → 状态 A；
    • 接 UARTRXDMASREQ（非空型）→ 不匹配，会超读，属于显然不能工作的接线。

8. 硬件 FIFO 溢出（OE）与开 DMA 的关系 ★最终结论★

前提：假设 DMA 能正常运行。

结论：能规避。

原因：

OE 的充分条件是「FIFO 满（32 字节）时没人把它读走」。

  • PIO 模式：读走依赖 CPU 在中断里响应，窗口只有 (32 - 16) = 16 字节的时间

    • 115200 → 1.39 ms
    • 460800 → 347 µs
    • 1 Mbps → 160 µs
    • 4 Mbps → 40 µs

    任何超过窗口的中断延迟（长 spinlock、关中断、IRQ 风暴、CPU 降频等）都 OE。

  • DMA 模式：FIFO 一到水位（16 字节）硬件就发请求、DMAC 直接把数据搬进内存，全程不需要 CPU 参与；CPU 晚几十毫秒也不影响 FIFO 被抽干。有效缓冲从 32 字节变成 4KB（PAGE_SIZE）的 DMA 页。

对「单次交互 < 一页」的流量：

  • 硬件 FIFO 由 DMA 实时抽空 → 不再 OE；
  • 由于不足一页，DMA 完成中断基本用不到，收尾全部走 RTI（32 bit 时间的固有延迟）；
  • 若上层来不及消费，丢数据发生在 tty 层（icount.buf_overrun），不再是硬件 OE。

唯一残留窗口：pl011_dma_rx_irq() 里先把 RXDMAE 关掉、交付完再重新打开的几微秒，此期间只有 32 字节 FIFO 顶着。按小包 + 包间有空档的流量特征，这个窗口远小于填满 32 字节所需时间，实际不会溢出。

补充（连续大流量才需要关注的失效模式）：

  • DMAONERR：一旦真的发生一次溢出，硬件会停掉 RX DMA 请求，错误标志要等 RTI 路径来清。连续不断的流可能长时间没有 32 bit 空档 → 可能停在「溢出—DMA 停—继续溢出」状态，直到流中断才自愈。小包/请求-响应型流量天然有空档，会自愈得快。auto-poll 对此没有帮助：它只读 residue 交数据，不碰错误标志，也不重新使能 RXDMAE。
  • 4KB 页填满后，DMA 完成回调跑在 tasklet/软中断里，若被长时间延迟，FIFO 也可能溢出（连续流才会命中）。
