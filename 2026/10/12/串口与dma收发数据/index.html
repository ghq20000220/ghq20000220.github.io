串口与dma收发数据

分析串口在开启dma时，如何进行数据的收发

环境

  • linux：5.10.227
  • 串口：pl011
  • dma：pl330

================================================================================
Linux 5.10 ARM PL011 串口 RX DMA 接收流程与硬件 FIFO 溢出问题 笔记
（PL011 + PL330 / PL080，主线驱动 amba-pl011.c）

结论速览

  1. PL011 的 RX DMA 是「单描述符、非 cyclic」：每次提交一个 scatterlist 条目，
    长度 PL011_DMA_BUFFER_SIZE = PAGE_SIZE（4K 页内核 = 4096 字节）。

  2. DMA 完成中断在「整页搬满」时才产生一次；不足一页不会有 DMA 中断。

  3. 不足一页的数据靠 PL011 自己的 RTI（接收超时中断）交付。

  4. 「FIFO 到了水位就搬、一次一个 burst」是硬件+DMAC 行为，与 CPU 无关。

  5. PL011 + PL330 在 Linux 5.10 下属于「健康路径（状态 A）」：水位 16 > burst 8，
    DMA 不会把 FIFO 抽干，RTI 必定会触发。

  6. 针对硬件 FIFO 溢出（OE）：假设 DMA 正常运行，开 DMA 可以规避。
    原理：读走 FIFO 的动作从「CPU 在中断里响应」变成「硬件到水位自动搬走」。

  7. 代码位置与关键常量

drivers/tty/serial/amba-pl011.c （PL011 驱动本体）
drivers/dma/pl330.c （PL330 DMAC，_bursts() 决定请求类型）
include/linux/amba/serial.h （寄存器位定义）

#define PL011_DMA_BUFFER_SIZE PAGE_SIZE /* 一次 DMA 的搬运长度 = 4096 */

struct pl011_sgbuf { /* 每个 buffer 恰好一个 sg entry */
struct scatterlist sg;
char *buf;
};
struct pl011_dmarx_data {
struct dma_chan chan;
struct pl011_sgbuf sgbuf_a, sgbuf_b; / 双缓冲 A/B /
dma_cookie_t cookie;
bool running;
struct timer_list timer; / 可选 poll 定时器 */
unsigned int last_residue;
unsigned long last_jiffies;
bool auto_poll_rate;
unsigned int poll_rate;
unsigned int poll_timeout;
};

RX 侧 DMA 参数（pl011_dma_probe）：
.src_addr = mapbase + REG_DR
.src_addr_width = DMA_SLAVE_BUSWIDTH_1_BYTE
.direction = DMA_DEV_TO_MEM
.src_maxburst = uap->fifosize >> 2 /* 32 深 FIFO → 8 字节/burst */
.device_fc = false

TX 侧是 .dst_maxburst = uap->fifosize >> 1（发送方向不需要给 FIFO 留尾巴）。

FIFO 水位（pl011_startup 里写 REG_IFLS）：
ARM 变体 = UART011_IFLS_RX4_8 = 1/2 FIFO = 16 字节（32 深 FIFO）
ST 变体 = UART011_IFLS_RX_HALF = 32 字节（64 深 FIFO）

DMACR：
UART011_RXDMAE (bit0) 使能接收 DMA 请求
UART011_TXDMAE (bit1) 使能发送 DMA 请求
UART011_DMAONERR (bit2) 出错时硬件停止 DMA 请求 ← 启动时由驱动置上

前置检查：如果 DMA 控制器汇报 residue_granularity ==
DMA_RESIDUE_GRANULARITY_DESCRIPTOR，驱动直接禁用 RX DMA（全流程依赖 residue）：
“RX DMA disabled - no residue processing”

  1. 接收流程（DMA 模式）

2.1 启动
pl011_startup → pl011_dma_startup → pl011_dma_probe（申请 tx/rx 通道、
slave_config）→ 置 DMAONERR → pl011_dma_rx_trigger_dma()：

    desc = dmaengine_prep_slave_sg(rxchan, &sgbuf->sg, 1, DMA_DEV_TO_MEM,
                                   DMA_PREP_INTERRUPT | DMA_CTRL_ACK);
    desc->callback = pl011_dma_rx_callback;
    dmarx->cookie = dmaengine_submit(desc);
    dma_async_issue_pending(rxchan);
    uap->dmacr |= UART011_RXDMAE;   /* 打开 UART 的 RX DMA 请求 */
    uap->im    &= ~UART011_RXIM;    /* 关掉 FIFO 阈值中断 */

pl011_enable_interrupts() 里 im = RTIM（DMA 在跑时不再补 RXIM），
也就是 DMA 模式下只有超时中断和 modem 中断能打断 CPU。

2.2 硬件握手（无中断、无 CPU）
RX FIFO 超过水位 → PL011 断言突发请求 → DMAC 按 burst 搬运 → FIFO 降回水位下
→ 请求撤销 → 再涨到水位再搬……直到整页（4096）搬满 → DMA 完成中断。

2.3 路径 A：整页搬满 → DMA 完成中断 → pl011_dma_rx_callback()
device_tx_status() 取 residue
pending = sg.length - residue （正常就是 4096）
dmaengine_terminate_all()
切到另一块 buffer → pl011_dma_rx_trigger_dma() 立刻重新点火
pl011_dma_rx_chars(pending, lastbuf, readfifo = false) ← 不动 FIFO

2.4 路径 B：不足一页 → RTI（接收超时中断）→ pl011_int → pl011_dma_rx_irq()
dmaengine_pause() ← 必须先暂停再读计数
device_tx_status() 取 residue
dmacr &= ~RXDMAE ← 关请求，数据先留在 FIFO
dmaengine_terminate_all()
pl011_dma_rx_chars(pending, use_buf_b, readfifo = true)
├─ 先从 DMA buffer 取 pending 字节送 tty
└─ 若全部塞入成功，再 pl011_fifo_to_tty() 把 FIFO 尾段读走（最多 256）
切 A/B buffer → pl011_dma_rx_trigger_dma() 重新点火

2.5 路径 C：接收错误（OE/BE/PE/FE）
因为 DMAONERR 已置位，硬件会自动停掉 RX DMA 请求，数据堆在 FIFO；
驱动的错误中断位（OEIM/FEIM/…）并未使能，最终仍走 RTI 路径，
由 pl011_dma_rx_chars() 里的
pl011_write(UART011_OEIS|BEIS|PEIS|FEIS, uap, REG_ICR)
清标志，然后重新 trigger DMA。

2.6 路径 D（可选）：poll 定时器，见第 6 节。

  1. DMA 中断到底要多少数据才触发
  • 一次 DMA 完成中断 = 一个描述符搬完 = PL011_DMA_BUFFER_SIZE = PAGE_SIZE
    • 4K 页内核：4096 字节
    • 16K / 64K 页内核：16384 / 65536 字节
  • 每个 burst（8 字节）、每次水位跨越，都【不】产生中断。
  • 非 cyclic、只有一个 sg entry，所以没有半传输中断。
  • 不足一页的数据：不会产生 DMA 中断，只能靠 RTI 交付。

DMA 完成回调里的注释印证：
“This completion interrupt occurs typically when the RX buffer is totally
stuffed but no timeout has yet occurred.”

  1. RTI（接收超时中断）的触发条件

ARM 文档原文（Linux/QEMU/Xen 多方引用一致）：
“The receive timeout interrupt is asserted when the receive FIFO is not
empty, and no more data is received over a 32-bit period. The receive
timeout interrupt is cleared either when the FIFO becomes empty through
reading all the data (or by reading the holding register), or when a 1 is
written to the corresponding bit of the UARTICR register.”

拆解：
(1) IMSC.RTIM = 1（bit6） —— 软件使能；Linux 在 DMA 模式下始终保留
(2) RIS.RTIS = 1（bit6） —— 硬件条件：FIFO 非空 + 32 bit 时间无新数据
(3) LCR_H.FEN = 1 —— FIFO 模式（驱动 fifosize>1 时必置）
(4) IRQ 线路通（合并 UARTINTR 或独立 UARTRTINTR）

时间与波特率相关，32 个 bit 时间 = 32/baud：
115200 → 约 278 µs
9600 → 约 3.33 ms
300 → 约 107 ms
要点：

  • 每收到一个新字符，32 bit 时间的计数器就重新开始（连续的流永不超时）。
  • 判据是「FIFO 非空」这个状态，与是否跨过 IFLS/RXIS 阈值无关。
  • FIFO 被读空 → 条件不成立，中断自动撤销；也可写 ICR.RTIC 清。
  • Linux 的 pl011_int() 特意不把 RTIS/RXIS 写进 ICR：
    pl011_write(status & ~(UART011_TXIS|UART011_RTIS|UART011_RXIS), uap, REG_ICR);
    靠把 FIFO 读空自然撤销，避免误清丢事件。
  • ST 变体有可编程超时寄存器 ST_UART011_TIMEOUT（偏移 0x0C），主线驱动不用。
  1. 关键判据：水位(IFLS) 与 burst(maxburst) 的大小关系

PL011 有四条 DMA 请求线（refman 原文）：
UARTRXDMASREQ 单字符请求：FIFO 含至少 1 个字符即断言
UARTRXDMABREQ 突发请求 ：FIFO 字符数超过 IFLS 编程的水位时断言
UARTRXDMACLR 由 DMAC 断言，清除接收请求；突发传输时在 burst 最后一个
数据传输期间断言
所以「一次搬多少」= DMAC 配的 burst 长度，不是「FIFO 里有多少」。
burst 是不可打断的传输组，做完才重新采样请求线。

    | 配置                        | 一次授权后      | FIFO 留尾巴 | RTI  |
    |-----------------------------|-----------------|-------------|------|
    | 水位 16 > burst 8（Linux 默认）| 16 → 8，请求撤销 | 留 8~15 字节 | 必触发 |
    | 水位 16 = burst 16          | 16 → 0          | 抽干        | 不触发 |
    | 水位 4  < burst 8           | 4 → 0（整数倍搬空）| 抽干       | 不触发 |

三种状态：
状态 A（健康）：停手时 FIFO 非空 → RTI 必来 → 数据不丢不延迟。
状态 B（延迟）：FIFO 被抽干但后续还有数据 → 下一批触发 RTI 或整页满才交付。
状态 C（滞留）：FIFO 被抽干且对端不再发 → 数据卡在 DMA buffer，上层读不到。

历史佐证（2013 LKML「PL011 Rx DMA buffer polling」讨论）：

  • Chanho Min：4096 字节由 DMA 中断收到，但剩下 904 字节拿不到，
    除非再来 3192 字节。（状态 C）
  • Linus Walleij：理论上 16 个字符会被两个 burst 搬空、FIFO 为空、页未满，
    既无 TC 中断也无 RTI；但他在 U300/Ux500 上从未复现，怀疑 PL011 IP 在
    burst 信号逻辑上做了处理。
  • Russell King：在 Versatile（PL080+PL011）上确实遇到，最后选择完全不开 RX DMA。
  1. auto-poll（可选软件轮询）

是什么：用一个内核定时器周期性读 DMA residue，把「已搬进内存、但还没有任何中断
交付」的字节直接塞给 tty；不打断 DMA、不 terminate 描述符。

核心函数 pl011_dma_rx_poll()：
device_tx_status() 取 residue
交付区间 [last_residue, residue) → tty_insert_flip_string
mod_timer(…) 继续；若超过 poll_timeout 无数据 → 停 DMA、开 RXIM、
terminate、删定时器，回落到纯中断模式

去重：pl011_dma_rx_chars() 里 dmataken = sg.length - last_residue，
跳过轮询已交付的字节；交付完把 last_residue 重置为整页。

如何打开：
DT（5.10 binding 有文档 Documentation/devicetree/bindings/serial/pl011.yaml）：
auto-poll; /* 必须显式打开，否则下面两个无效 /
poll-rate-ms = <10>; / 默认 100 /
poll-timeout-ms = <3000>; / 默认 3000 */
或平台数据：struct amba_pl011_data { .dma_rx_poll_enable = true; … }

⚠ 已知坑：DT 分支不会清 auto_poll_rate（5.10 与 6.6 都一样），
于是每次 pl011_set_termios()（打开端口、stty、改波特率）都会覆盖：
if (uap->dmarx.auto_poll_rate)
uap->dmarx.poll_rate = DIV_ROUND_UP(10000000, baud);
即 115200 → 87 ms，3 Mbps → 4 ms，9600 → 1042 ms。
想固定周期只能走平台数据路径或改驱动。
平台数据分支会正确把 auto_poll_rate 置 false。

代价：每 poll_rate 一次定时器唤醒，妨碍 CPU 深度 idle、影响省电与实时性。
默认关闭是对的，只在确实出现状态 B/C 时才开。

  1. PL011 + PL330 在 Linux 5.10 下属于哪种状态

代码证据链（drivers/dma/pl330.c）：
pl330_config_write(): pch->burst_len = fixup_burst_len(src_maxburst) /* = 8 */
pl330_prep_slave_sg(): desc->rqcfg.brst_len = pch->burst_len
_prepare_ccr(): CCR.SRCBRSTLEN/DSTBRSTLEN = brst_len
_bursts(): cond = BRST_LEN(ccr) > 1 ? BURST : SINGLE
→ 8 > 1 → BURST
_ldst_peripheral(cond=BURST): DMAFLUSHP → [DMAWFPB → DMALDPB → DMAST] × N

即：PL330 等的是外设的「突发请求」，一次请求搬一个 burst = 8 字节。

结论：PL011 水位 16 > burst 8，每次授权后 FIFO 从 ≥16 掉到 ≥8，请求撤销，
停手时必留 8~15 字节 → RTI 必触发 → 【状态 A（健康路径）】。
2013 年 Linus 担心的「整数倍突发被搬空」在这个组合下不会发生。

附带结论：

  • residue_granularity = DMA_RESIDUE_GRANULARITY_BURST，且 pl330_tx_status()
    通过读 SA/DA 寄存器算出字节级 residue，满足 PL011 驱动的前置要求。
  • arm,pl330-periph-burst quirk 对 PL011 RX 无影响（burst_len 已是 8 > 1）；
    它只对 burst_len == 1（maxburst 配成 1）的场景有意义。
  • 唯一无法从代码确定的是 SoC 把 PL011 的哪根请求线接到 PL330：
    接 UARTRXDMABREQ（水位型）→ 与 BURST cond 匹配 → 状态 A；
    接 UARTRXDMASREQ（非空型）→ 不匹配，会超读，属于显然不能工作的接线。
  1. 硬件 FIFO 溢出（OE）与开 DMA 的关系 ★最终结论★

前提：假设 DMA 能正常运行。

结论：能规避。

原因：
OE 的充分条件是「FIFO 满（32 字节）时没人把它读走」。

  • PIO 模式：读走依赖 CPU 在中断里响应，窗口只有 (32-16)=16 字节的时间
    115200 → 1.39 ms 460800 → 347 µs 1 Mbps → 160 µs 4 Mbps → 40 µs
    任何超过窗口的中断延迟（长 spinlock、关中断、IRQ 风暴、CPU 降频等）都 OE。
  • DMA 模式：FIFO 一到水位（16 字节）硬件就发请求、DMAC 直接把数据搬进内存，
    全程不需要 CPU 参与；CPU 晚几十毫秒也不影响 FIFO 被抽干。
    有效缓冲从 32 字节变成 4KB（PAGE_SIZE）的 DMA 页。

对「单次交互 < 一页」的流量：

  • 硬件 FIFO 由 DMA 实时抽空 → 不再 OE；
  • 由于不足一页，DMA 完成中断基本用不到，收尾全部走 RTI（32 bit 时间的固有延迟）；
  • 若上层来不及消费，丢数据发生在 tty 层（icount.buf_overrun），不再是硬件 OE。

唯一残留窗口：pl011_dma_rx_irq() 里先把 RXDMAE 关掉、交付完再重新打开的几微秒，
此期间只有 32 字节 FIFO 顶着。按小包 + 包间有空档的流量特征，这个窗口远小于
填满 32 字节所需时间，实际不会溢出。

补充（连续大流量才需要关注的失效模式）：

  • DMAONERR：一旦真的发生一次溢出，硬件会停掉 RX DMA 请求，错误标志要等
    RTI 路径来清。连续不断的流可能长时间没有 32 bit 空档 → 可能停在
    「溢出—DMA 停—继续溢出」状态，直到流中断才自愈。
    小包/请求-响应型流量天然有空档，会自愈得快。
    auto-poll 对此【没有】帮助：它只读 residue 交数据，不碰错误标志，
    也不重新使能 RXDMAE。
  • 4KB 页填满后，DMA 完成回调跑在 tasklet/软中断里，若被长时间延迟，
    FIFO 也可能溢出（连续流才会命中）。
  1. 诊断与验证命令

硬件 FIFO 溢出 vs 软件丢字节（需要 root 才打印计数字段）

cat /proc/tty/driver/ttyAMA

0: uart:PL011 rev3 mmio:0x… irq:33 tx:.. rx:.. oe:N bo:M

oe = icount.overrun 硬件 FIFO 溢出（UART011_DR_OE）

bo = icount.buf_overrun tty 缓冲满丢字节（tty_insert_flip_char 返回 0）

确认 RX DMA 真的起来了（而不是悄悄退回中断模式）

dmesg | grep -i “DMA channel” # 期望同时有 “DMA channel TX …” 和 “DMA channel RX …”

中断来源指纹

cat /proc/interrupts

交互敲键 → uart/pl011 计数涨；大批量传输 → DMAC 大约每 4KB 涨一次

每包「两段」分布（dynamic debug）

echo ‘file amba-pl011.c +p’ > /sys/kernel/debug/dynamic_debug/control
dmesg -w | grep “Took”

“Took %d chars from DMA buffer and %d chars from the FIFO”

发 8 字节(<水位) → 期望 0 and 8

发 16 字节(=水位) → 8 and 8 或 0 and 16（取决于「≥水位」还是「>水位」）

驱动自带的两条关键告警

could not retrigger RX DMA job, fall back to interrupt mode

couldn’t insert all characters (TTY is full?)
