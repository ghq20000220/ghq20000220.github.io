Agent在嵌入式软件开发中的应用分析

结论

Agent在嵌入式C开发中的能力边界，主要由“反馈”决定。凡是正确性可以被编译器、静态分析器或主机侧测试判定的工作，Agent 已经明显优于人工；凡是正确性依赖于运行时交错、物理时序或目标机不可见状态的工作，Agent 目前基本无法独立完成，且失败方式具有欺骗性——它会给出逻辑自洽但错误的结论

主要结论：

  • 编写：Agent 擅长模板化、契约显式、可被工具验证的代码（外设初始化、协议编解码、状态机、错误码框架、测试与文档）；弱于并发正确性、硬件时序、未定义行为与编译器优化的交互、资源预算取舍。
  • 调试：编译/链接错误修复是 Agent 最强的场景（估计快 5–20 倍）；HardFault 现场分析、有可复现测试的逻辑 bug 表现良好；需要示波器观测、间歇性时序 bug、多因素耦合问题表现差，且幻觉式根因是最危险的失败模式。
  • 外设驱动：能力随「正确性依赖代码文本之外信息的程度」单调下降。可分为 L0–L4 五级，L0–L1 可独立完成，L3（DMA/并发）与 L4（低功耗）必须人先定契约。
  • 标准 vs 非标驱动：差距稳定在 20–30 个百分点。原因不是标准驱动”更简单”，而是契约进入了可读范围——参数里有超时、返回值里有状态、语料里有模板、审核者脑子里有先验。
  • 资料准备：给 Agent 的不是”整本手册”，而是机器可读的事实源（DMA 请求表、勘误表）+ 人写的契约 + 可执行的验证手段。
  • 经济性：标准驱动 + Agent 的净收益显著为正（约 3–4 倍）；非标驱动在资料准备和审核上双重付费，可能打平甚至为负。“让 Agent 逆向出契约草稿、人来审”并非普适最优——只在原作者已不在、驱动规模足够大、且契约会被反复使用时成立。
  • 人的介入点：性价比最高的是只审接口（20–40 行），而不是审实现（500 行）。接口是唯一不可逆、体量最小、影响面最大的东西。
  • 自由发挥的代价是结构化的：降的是系统一致性（错误码、命名、生命周期、并发假设、API 面），不是单点正确性。因此小规模一次性场景可以放手，跨模块长期演进必须钉住接口。

问题背景

嵌入式软件开发的几个固有特征，使它成为检验 Agent 能力的”极限场景”：

  • 反馈慢且贵：编译、烧录、复位、观测，一轮迭代从分钟到小时级。
  • 状态不可见：程序状态在目标机 RAM 中，缺少调试器接口时只能靠 printf，而 printf 本身改变时序。
  • 上下文庞大：HAL/SDK + RTOS + 应用，关键配置散落在数十个文件中。
  • 错误代价高：验证成本远高于生成成本。

软件开发任务特点分析

  • 从上述分析表格可以看出，裸机驱动和一些没有标准驱动接口的应用开发对于Agent较难。存在标准接口的应用开发Agent存在优势

模型知识方面：

  • 模型相关知识不足时，Agent表现差

    • 对于底层驱动开发，可以通过提供硬件资料给Agent。提高模型相关知识。同时需要注意精简资料信息，避免模型注意力被过度稀释
    • 对于没有标准驱动的应用开发，可以通过给驱动的接口定义和功能。

  • 模型知识充足时，Agent开发存在显著优势

    • 比如linux应用开发。模型训练时有充足语料。无需提供额外资料即可进行应用开发且表现良好。

硬件耦合方面：

  • 硬件耦合低：
    • linux应用开发，用户态不操作寄存器与硬件零耦合。失败后可以kill重来。基本无需重新烧录重启系统。可以使用gdb，strace等工具。
  • 硬件耦合高：
    • 驱动开发，涉及寄存器操作。需要复位烧录，耗时相比较长。难以获取硬件实际状态，当需要使用示波器等硬件时，Agent无法独立完成。需要人介入

成本分析

关于Token，一个中等模块，资料 30k + 对话 20k×20 轮 ≈ 400–500k 输入、20k 输出，按常见 API 价格折算约 1 元。即使模型贵 10 倍也只有 10 元，对比人工的百元千元量级。占比极低。结论：token成本可以忽略不记。

Skill 是什么(https://www.dorabc.com/articles/agent-skill-guide/)

Skill 是一个文件夹。里面有一个名为 SKILL.md 的文件。这个文件由两部分组成：一段简短的头部信息，用 YAML 写成，包含 Skill 的名称和描述；以及一个正文，用普通 Markdown 写成，包含 Agent 应该遵循的实际指令
